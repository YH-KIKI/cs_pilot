## 재현해 확인한 원인과 수정

### O04: 조회만으로 답변을 제안해 정책 근거 조건에 막힘

[수정 전 진단](agent-diagnostic-before-2026-10-30.json)에서 실제 모델이 주문 조회 후 10월 23일 예상 배송일을 답변했지만 search_policy는 실행하지 않았다. 날짜 사실은 조회와 일치했으나 서비스가 요구하는 정책 근거 포함 답변 계약을 충족하지 못했다.

수정: 검색 없이 answered를 제안했고 아직 판단 횟수가 남아 있으면 서버 feedback으로 판단 노드에 돌려보낸다. 모델이 검색 행동·검색어를 다시 선택한다. 서버가 검색을 실행한 것처럼 이력을 만들거나 검색어를 대신 정규화하지 않는다. 모델 4회·도구 3회 한도는 그대로고, 계속 검색하지 않으면 근거 부족으로 종료한다. 최종 실제 재평가에서 주문 조회·정책 검색·예상일 안내를 모두 충족했다.

### E01: 계획 스키마의 nullable 값과 최종 응답 계약 불일치

실제 진단에서 모델은 insufficient_evidence를 선택했지만 recommendation=null이었다. 도구 행동과 최종 행동을 함께 표현하는 NextAction은 이를 허용하지만, ConsultationResponse는 Recommendation 객체를 요구해 `recommendation / model_type` 검증 오류가 발생했다. 구조화 JSON에 맞는다는 것이 최종 업무 계약까지 충족한다는 뜻은 아니었다.

수정: 근거 부족 상태의 recommendation만 비어 있으면 수집 정책의 한계와 추가 확인 절차를 안내하는 고정 문장을 채운다. 규정/금액을 만들지 않고, 고객 초안은 null로 유지한다. 잘못된 인용 등 다른 검증을 통과시켜 주지는 않는다. 실제 최종 실행은 모델이 정상 추천을 작성해 insufficient_evidence로 끝났고, null 복구 자체는 진단과 같은 출력을 넣은 회귀 테스트로 확인했다.

### 주문 조회 생략: 선택한 대상 주문의 의미를 서버에서 고정

이전에는 주문번호가 입력돼도 모델이 requires_order=false로 분류하면 조회가 생략됐다. 입력한 번호는 상담원이 선택한 대상 주문으로 해석하고 초기 requires_order=true로 둔다. 일반 정책만 묻는 경우에는 번호를 비운다. 질문 문장의 단어나 조사로 주문번호를 추출하거나 분류 규칙을 추가하지 않았다.

최종 O08/O10/R02/F01은 모두 실제 주문을 조회했다. O08에는 14일 계산도 포함됐다. O08의 남은 상태 문제와 R02의 문장 해석 문제는 아래처럼 별도로 남긴다.

### 기간 경과와 경계일의 마감시각을 구분

중간 평가 O09는 15일이 경과했다고 계산/설명하면서도 경계일 마감시각 미확인을 이유로 needs_information을 반환했다. 프롬프트 v3에서 이미 일반 기간을 넘은 사실 안내와 정확한 경계시각 확인을 구분했다. 최종 O09는 15일 경과를 answered로 안내했고 다른 권리를 부정하지 않았다.
