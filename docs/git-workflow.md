# CS Pilot Git 운영 규칙

일주일짜리 개인 MVP에서 빠른 개발과 검토 가능한 변경 이력을 함께 확보한다.
이 문서는 작업 규칙이며 브랜치·커밋·PR을 자동으로 생성하지 않는다.

## 1. 브랜치

- `main`은 검증한 변경을 모으는 기준 브랜치다.
- 기능·수정·문서 등 목적별로 짧게 사용하는 작업 브랜치를 두며 `develop`은 만들지 않는다.
- `feat/rag-retrieval`, `fix/order-item-mapping`, `docs/git-workflow`처럼 목적을 이름에 쓴다. 날짜를 브랜치의 주 식별자로 사용하지 않는다.
- 하나의 검토 가능한 목적이 끝나면 diff와 필요한 검증을 확인하고 `main`에 병합한다.
- PR 없이 병합하는 경우에도 동일하게 검토·검증한다. 모든 커밋마다 별도 브랜치나 PR을 만들 필요는 없다.
- 병합 후 완료한 작업 브랜치를 정리한다. 병합되지 않은 커밋이나 다른 워크트리에서 사용 중인 브랜치는 임의로 삭제하지 않는다.
- merge/squash/rebase 방식 자체를 일괄 강제하지 않는다. 목적이 분명한 커밋은 보존하고 불필요한 이력 재작성을 피한다.

작업 시작 전에 현재 변경이 있는지 확인한다. 기존 변경이 있으면 소유·목적을 파악하고 보존한다. 다른 브랜치로 이동하려고 무조건 stash·reset·clean을 실행하지 않는다. 새 브랜치 생성 등 실제 Git 변경은 해당 작업의 요청 범위에서 수행한다.

## 2. 커밋

하나의 분명한 목적을 가진 작은 변경 단위로 나눈다. 같은 목적의 코드·테스트·계약·문서 수정은 함께 묶을 수 있다. 관련 없는 기능·정리·문서를 섞지 않는다. 파일 수나 작업한 날짜만으로 단위를 정하지 않는다.

간단한 Conventional Commits 형식을 사용한다.

```text
종류(선택적 범위): 구체적인 변경 내용
```

| 종류 | 용도 | 예시 |
|---|---|---|
| feat | 새 기능 | feat(orders): SQLite 주문과 품목 조회 추가 |
| fix | 동작 오류 수정 | fix(rag): 반품 검색에서 예외 조건 누락 수정 |
| docs | 문서 변경 | docs: Git 운영 규칙 정리 |
| chore | 환경·설정·유지 관리 | chore: Python과 프런트 의존성 고정 |
| test | 검증 보강 | test(agent): 재검색과 호출 상한 검증 추가 |
| refactor | 기능 변화 없는 구조 개선 | refactor(orders): SQL 결과 매핑 함수 분리 |

`update`, `작업 완료`, `day2`처럼 변경을 알기 어려운 메시지는 피한다. 본문은 이유·주의점이 필요할 때만 덧붙인다. 동작·계약이 바뀌면 refactor나 docs라는 이름으로 축소하지 않는다.

스테이징은 목적에 맞는 경로나 변경 구간을 선택한다. 이미 진행 중인 다른 변경이 있는 상태에서 일괄 추가로 섞지 않는다. 커밋 전에는 작업 폴더 diff뿐 아니라 실제 스테이징된 diff도 확인한다. 과거 이력을 보기 좋게 만들기 위한 force push·불필요한 커밋 재작성은 하지 않는다.

## 3. PR을 남기는 기준

모든 커밋이나 사소한 작업에 PR을 요구하지 않는다. 핵심 설계와 결과 동작을 나중에 설명할 수 있어야 하는 변경에는 PR을 남긴다.

| 중요한 변경 예 | PR에 남길 검토 포인트 |
|---|---|
| SQLite 주문 구조·조회 도구 | 1:N·PK/FK·품목별 상태, 초기화 재현성, SQL 바인딩, 읽기 전용 계약 |
| RAG 적재·검색 | 조건/예외 보존, 임베딩·인덱스 버전, 출처 반환, 검색 평가 |
| LangGraph 흐름·실행 제한 | 상태·분기·반복·종료, 도구 선택, 재검색·전체 호출 상한 |
| 배포 | 단일 서비스 구성, 고정 데이터 복원, 설정·키 처리, 실제 배포 검증 |

PR 필요 여부는 확장자나 디렉터리가 아니라 **동작·데이터·API 계약에 미치는 영향**으로 판단한다. 예를 들어 정책 본문·SQL 시드·평가 정답·OpenAPI JSON은 데이터/문서 파일이어도 결과 판단과 계약에 영향을 주므로 중요 변경이 될 수 있다. 오탈자·설명 보완·동작 영향 없는 작은 정리는 검토와 검증 후 PR 없이 병합할 수 있다.

핵심 PR은 전체 3~5개 정도를 예상한다. 숫자를 맞추려고 억지로 쪼개거나 무관한 변경을 합치지 않는다. 하나의 핵심 PR에 목적이 구분되는 여러 작은 커밋을 포함할 수 있다. 이미 완료·병합된 작업을 기록용 PR로 만들려고 과거 커밋을 되돌리거나 새 이력을 꾸미지 않는다. 기존 기록이 있다면 문서와 해당 커밋을 연결한다.

PR 사용 시 자체 검토만으로도 충분하다. 별도 검토자 확보나 형식적인 승인을 이 개인 MVP의 필수 단계로 추가하지 않는다.

## 4. 검토와 검증

PR 유무와 관계없이 변경 diff를 읽고 의도하지 않은 파일·비밀값·계약 변경이 없는지 확인한다. 추적하지 않는 신규 파일은 일반 `git diff`에 표시되지 않으므로 파일 내용도 검토한다. 커밋 단계에서는 스테이징된 diff가 최종 검토 대상이다.

변경에 맞는 검증을 선택한다. 아래는 선택 기준이며 매번 모두 실행하라는 체크리스트가 아니다.

| 변경 | 적절한 검증 예 |
|---|---|
| 문서만 수정 | 내용·상대 링크·기존 지침 충돌 확인, git diff --check |
| SQLite·주문 도구 | 관련 pytest, PK/FK·1:N 매핑·읽기 전용·없는 주문/오류·초기화 재현성 |
| 정책·평가 자료 | 출처/수집일/해시·조건/예외·고정 날짜 및 평가 정의 검증 |
| API·프런트 타입 | 관련 pytest, npm run typecheck, npm run check:contracts, 필요한 경우 빌드 |
| RAG·LangGraph | 검색/흐름 관련 테스트와 평가, 근거 부족·오류·실행 한도 경로 |
| 환경·배포 | 잠금 파일 기반 설치/빌드, UI/API 상태, DB·인덱스 복원과 재시작 |

구체적인 명령은 [README](../README.md), [평가 문서](evaluation.md), [API 계약](api-contract.md)을 따른다. 기존 [환경 검증 기록](environment.md)은 당시 결과이며 이후 변경까지 자동으로 검증한 것으로 간주하지 않는다. 문서만 수정할 때 유료 AI 호출이나 전체 Docker 빌드를 요구하지 않는다.

실제로 실행한 검사·결과만 기록한다. 실행하지 못한 항목은 미실행과 이유를 명시한다. 모의 도구·계약 예시 검증을 실제 검색·AI 품질 검증으로 표현하지 않는다. 검사 실패가 있으면 수정 후 관련 검사를 확인하고, 해결하지 못한 제한은 보고한다.

완료 보고는 다음을 짧게 포함한다.

```text
변경: 해결한 문제와 결과
검증: 실제 실행한 검사와 결과; 미실행 항목이 있다면 이유
Git: 현재 브랜치, 생성한 커밋 해시 또는 미커밋, PR 링크/없음/미생성 및 이유
```

보고 형식 때문에 별도 보고 파일이나 자동화를 매번 만들 필요는 없다.

## 5. PR 설명

대화 내용을 모르는 사람이 읽어도 문제와 결과 동작을 이해할 수 있게 쓴다.

- 해결하려는 문제와 변경 이유
- 주요 변경 및 결과 동작
- 실제 검증 방법과 결과(미실행 구분)
- 중요한 설계 선택·남은 제한이 있을 때만 추가 설명

단순한 변경은 짧은 문단과 검증 결과면 충분하다. 변경 범위가 달라지면 최종 범위에 맞춰 제목과 설명을 갱신한다. 작업 대화·폐기한 시도·실행하지 않은 검사 결과를 나열하지 않는다. 별도 PR 템플릿·hook·추가 CI는 이번 규칙을 위해 도입하지 않는다.

## 6. 버전 관리 대상과 생성물

| 구분 | 파일/경로와 원칙 |
|---|---|
| 코드·설정·계약 | Python/React 소스, 환경 구성, API 계약과 예시, 문서·검증 코드를 관리 |
| 주문 정의 | data/orders/schema.sql, seed_orders.sql, lookup_order.sql, manifest.json 관리 |
| 정책·평가 | 수집 원문·제목/URL/수집일/해시·검수 본문·selection, data/eval/cases.json 관리 |
| 의존성 | pyproject.toml, uv.lock, frontend/package.json, frontend/package-lock.json 관리 |
| 비밀값 | API 키·실제 .env 및 비밀값 포함 설정 제외. .env.example은 값 없는 예제로만 관리 |
| 주문 실행 DB | data/runtime/orders.sqlite3 등 생성 DB·임시 DB 제외. 스키마/시드에서 생성 |
| Chroma 실행 데이터 | data/runtime/chroma/ 등 런타임 폴더 제외. 로컬 DB와 고정 배포 자료를 혼합하지 않음 |
| 설치·실행 생성물 | .tools/, .venv/, node_modules/, 캐시·로그, frontend/dist/·app/static/ 제외 |
| 고정 배포 자료 | 기존 설계의 artifacts/embeddings.jsonl, artifacts/index_manifest.json 등 작은 검수 청크/벡터·명세를 런타임 폴더와 별도로 관리 |

고정 배포 자료에는 말뭉치·청킹·임베딩 모델/차원·해시를 연결한다. 기존 설계대로 이 자료에서 인덱스를 복원하고, 주문 DB는 고정 SQL 시드로 생성한다. 매 배포 시 유료 재임베딩하는 방식으로 바꾸지 않는다. 실제 고정 인덱스 산출물은 아직 없으며, 대용량 바이너리나 로컬 Chroma 디렉터리를 통째로 커밋하지 않는다. 크기가 커지면 재현 방법과 고정 버전을 먼저 정하고 배포 아티팩트로 관리할지 결정한다.

현재 `.gitignore`는 `data/runtime/`, 생성 SQLite 파일, 환경·설치 폴더·로그 등을 제외한다. Chroma 저장 경로를 새로 구현할 때 이 런타임 경로를 사용하고, 다른 경로라면 제외 여부를 확인한다. 규칙 문서화를 위해 이번에 `.gitignore`나 생성 데이터 위치를 변경하지 않는다.

## 7. 현재 상태와 다음 작업 제안

- 현재 브랜치: `main`, HEAD: `57e4243` (`Initial commit`). 로컬에 저장된 `origin/main`도 같은 커밋이다. 이번 확인에서 fetch하지 않았으므로 원격 서버 최신 상태를 새로 확인한 것은 아니다.
- 추적 중인 파일은 기존 .gitignore·README.md 두 개이며 둘 다 미커밋 수정이다. 1일차 구현·데이터·문서·잠금 파일은 아직 신규 미추적 상태다. 스테이징된 변경은 없다.
- 기존 AGENTS.md는 작업 폴더 및 확인한 상위 경로에서 발견하지 못했다. 이번에 루트 AGENTS.md를 추가해 이 문서를 연결한다.
- `YH-KIKI/murre`는 별도 워크트리에서 같은 초기 커밋을 사용 중이다. 현재 작업의 완료 브랜치로 간주하거나 정리하지 않는다.

먼저 현재 main의 미커밋 변경을 보존한 채 기반 구성용 브랜치로 옮겨 검토하는 것이 적절하다. 이미 Git에 병합된 작업의 기록용 PR을 새로 만드는 것이 아니다. 기존 커밋을 재작성할 이유가 없다. 목적이 연결되는 환경 설정, 주문 DB/도구, 정책/평가, 상담 계약 등의 작은 커밋으로 구분하되 정확한 파일·변경 구간은 실제 diff로 결정한다. 이번 Git 문서 변경도 구현 변경과 구분한다.

기반 구성을 정리한 다음 main을 기준으로 RAG 브랜치를 시작하면 새 기능과 기존 1일차 변경이 섞이지 않는다. 상담 결과 UI가 별도의 중요한 동작 변경으로 커지면 `feat/consultation-ui` PR을 추가할 수 있지만 화면 하나라는 MVP 범위는 유지한다. 이 안은 약 4개 핵심 PR을 예상한 것이며 필수 개수나 새로운 승인 절차가 아니다.
