# 주요 판단·문제 해결 기록

일차별 진행과 검증 목록은 [개발 기록](devlog/README.md)에 둔다. 여기에는 선택 이유·대안·문제 원인과 개선 차이만 남긴다. 기존 항목에 후속 결과를 덧붙이고 근거 없는 성과 수치나 예정된 해결을 기록하지 않는다. 특별한 판단·문제가 없으면 항목을 추가하지 않는다.

현재 항목은 사용자 지정 [1일차(2026-10-22)](devlog/day01-2026-10-22.md)에 연결한다. 원본 메타데이터와 도구 실행 시각은 보존한다. 과거 기록을 정리한 항목과 실제 실행 검증을 구분한다.

## D01. 프런트는 React + TypeScript + Vite, 화면은 하나

- **선택:** 초기 HTML/JS → Vite + TypeScript 구상에서 React + TypeScript + Vite로 변경했다. TypeScript를 요구하는 채용공고에 대비한 학습이 사용자 요구에 추가됐다.
- **검토 대안:** vanilla TypeScript는 설정과 화면 구현이 단순하지만 React props·상태 설계의 학습 범위가 줄어든다. 라우터·전역 상태 라이브러리·여러 화면은 일주일 MVP에 추가하지 않았다. 대안 비교는 설계 검토이며 구현별 성능 실험은 아니다.
- **적용/검증:** 주문 결과의 판별 유니온, nullable 날짜, props, 상태 라벨 매핑을 사용했다. strict 타입 검사·Zod 계약 검사·빌드가 통과했다.
- **한계:** TypeScript는 외부 JSON의 실제 형식이나 정책 판단을 보장하지 않는다. 런타임 응답은 Zod로 검사한다. 정책/AI 계약 타입은 있으나 결과 UI 연결은 남아 있다. [타입 사례](typescript.md)

## D02. 가상 주문을 JSON 조회에서 SQLite 1:N 조회로 변경

- **선택 이유:** SQL·관계·기본키/외래키를 설명할 수 있도록 orders와 order_items로 분리했다. 배송 상태·날짜는 주문 공통 정보가 아니라 품목 정보다.
- **검토 대안:** JSON은 소량 조회 구현이 가장 간단하지만 키 관계를 DB 제약으로 검사할 수 없다. 외부 DB·ORM은 이번 읽기 전용 소규모 MVP에 설정 부담이 커 도입하지 않았다.
- **적용:** 조회 도구의 found/not_found/error 계약은 유지했다. 고정 LEFT JOIN과 값 바인딩을 사용하고, 런타임 연결은 mode=ro다. DB 생성은 고정 SQL 시드와 별도 초기화 스크립트가 담당한다.
- **확인 결과:** PK/FK·수량 제약·품목별 상태·없는 주문과 DB 오류·읽기 전용·인젝션 형태 입력을 검사했다. 재초기화 및 Windows/컨테이너의 논리적 데이터 digest가 같았다.
- **한계:** 이는 가상 주문 조회 검증이며 실제 주문 시스템 연결이나 쓰기 기능은 아니다. 바이너리 파일 해시가 같아야 한다는 기준도 사용하지 않는다. [구현 설명](../README.md#sqlite-관계와-초기화)

## D03. 고정 정책 원문과 조건/예외 묶음을 RAG의 입력으로 사용

- **선택 이유:** 한 회사의 한국어 공개 정책으로 범위를 고정해 출처와 적용 조건을 추적한다. 실시간 웹검색·자동 갱신·큰 크롤러는 제외했다.
- **검토 대안:** 화면의 짧은 본문만 사용하면 반품 약관 오버레이와 제외 조건을 놓친다. 단순 길이 분할은 조건과 예외를 떼어낼 수 있어 규칙 묶음을 먼저 정리했다.
- **적용/확인:** 원문 3개와 해시·수집 시각을 보존하고 11묶음을 검수했다. 중복 약관은 반품 페이지를 기준으로 삼았다. 개발자의 검수 메모는 공식 본문과 분리했다. 출처·해시·정리 결과 검사가 통과했다.
- **미검증:** 묶음을 고려한 실제 청킹·임베딩·검색은 다음 단계다. 검색 품질이 좋아졌다는 수치는 없다. 수집일은 시행일이 아니며 시행일을 확인하지 못한 값은 null이다. [검수 근거](policy-review.md)

## D04. 상담 계약과 오프라인 평가 정의를 실행 기능보다 먼저 고정

- **선택 이유:** 주문 사실·근거·추가 확인·오류를 프런트와 백엔드가 같은 의미로 처리하게 하고, 약 4달러 예산에서 불필요한 유료 반복을 줄인다.
- **검토 대안:** 자유형 텍스트만 반환하면 출처 연결과 상태 처리를 검사하기 어렵다. 미구현 상담을 성공 응답으로 모사하지 않고 현재는 501을 반환한다.
- **적용/확인:** Pydantic/Zod·OpenAPI·6상태 예시와 고정 날짜의 평가 24사례를 만들었다. 잘못된 근거 ID·입력·누락 항목·응답 내 도구 횟수 등의 계약 검사가 통과했다.
- **한계:** 예시 검증은 실제 상담이나 실행 전 상한 차단의 검증이 아니다. LangGraph guard와 의미 기반 답변 평가는 미구현이다. 기준 날짜의 재현성도 모델 응답의 완전한 결정성을 보장하지 않는다. [계약](api-contract.md), [평가](evaluation.md)

## T01. HTML 정리 중 배송 안내 문단이 중복 추출됨

- **증상/원인:** 배송 도착 시간 정리본에 같은 지역별 안내가 두 번 나왔다. 원본의 중첩된 p/li를 모두 텍스트로 읽어 부모의 전체 내용과 자식 내용을 중복 수집했다.

- **전후/검증:** 수정 전에는 목록 전체 문장과 각 목록 문장이 반복됐다. 수정 후 로컬 원문으로 정리본을 재생성하고 출처·내용 해시·평가 정의 검증을 통과했다.
- **미검증:** 모든 웹페이지에 일반화되는 추출기나 RAG 검색 점수 개선으로 검증한 것은 아니다. 대상은 고정한 3페이지다. [추출 코드](../scripts/curate_policies.py)

## T02. Windows 출력·PowerShell 스크립트의 인코딩 문제

- **확인한 증상:** 정책 제목 출력에서 Python의 cp949 UnicodeEncodeError가 발생했다. 별도로 비ASCII 메시지가 있던 PowerShell 설치 스크립트의 ParseFile 구문 검사도 실패했다.
- **원인 구분:** Python 오류는 출력 인코딩이 해당 문자를 표현할 수 없어 발생했다. PowerShell은 ASCII 메시지로 바꾼 뒤 통과한 사실을 확인했으며, 환경별 코드페이지/인코딩 영향으로 판단했다. 정확한 디코딩 경로를 전수 분석하지는 않았다.
- **해결/검증:** 정책 관련 Python 명령에 -X utf8을 사용했고 정책 제목 출력이 성공했다. 설치 스크립트 메시지는 ASCII로 바꾸고 setup.ps1·uv.ps1 구문 검사를 통과했다. 시스템의 실행 정책과 기본 인코딩은 영구 변경하지 않았다. [환경 기록](environment.md)

## T03. 보존 커밋의 공백 검사와 원문 바이트 보존 충돌

- **증상/원인:** 최초 전체 스테이징 diff --check가 실패했다. 외부 HTML의 원래 공백과 -text로 보존한 파일의 CRLF까지 공백 경고에 포함됐다. 자체 코드의 기능 오류로 확인된 것은 아니다.
- **검토 대안:** 원문을 일괄 포맷하면 저장한 SHA-256과 원본 대조가 깨진다. Git 전체의 공백 검사를 끄지도 않았다.
- **해결/검증:** 원본 폴더만 제외한 스테이징 공백 검사는 통과했다. 원본 스냅샷 7파일은 index의 바이트 해시를 작업 파일과 대조했고 기존 75파일 내용도 보존됐다. 그 상태로 체크포인트 8a75a1e를 생성했다.
- **운영 범위:** 이후에도 원문 보존 예외는 해당 폴더에만 적용하고 자체 작성 파일의 검토를 생략하지 않는다. [원본 보존 규칙](policy-review.md), [일차 기록](devlog/day01-2026-10-22.md)

### D05. 규칙 단위 청킹과 테스트 벡터 분리 (2026-10-25)

- 선택: 검수한 11규칙을 통째로 청크로 만든다. 고정 길이 자동 분할·오버랩은 현재 작은 말뭉치에서 조건/예외를 분리할 수 있어 채택하지 않았다. 반품 절차와 별도 반품 조건은 명시적 관계로 함께 반환한다.
- API 검증 보류 중에는 의미 없는 해시 벡터를 별도 인덱스에 넣고 서비스와 동일한 저장·검색 코드를 검증한다. 테스트 통과를 실제 검색 품질로 해석하지 않으며 실제 도구가 테스트 인덱스를 대신 사용하지 않는다. 로컬 의미 임베딩 모델 추가는 배포 모델 검증을 대체하지 못하고 설정 범위를 늘려 이번에 도입하지 않았다.
- 검토 중 확인: 기존 인덱스 무결성 검사는 본문과 chunk_id만 대조했다. topic이 바뀌면 검색 필터가 달라질 수 있어 rule_group_id·topic을 포함한 메타데이터 대조로 보강했다. 실제 운영 장애나 검색 정확도 개선을 확인한 것은 아니다.
- 실제 검증: 오프라인 pytest 6개와 Chroma smoke 통과. 손상된 필터 메타데이터 거부, 반복 적재와 별도 프로세스의 캐시 재사용을 확인했다. 실제 의미 검색 전후 점수는 없다. [2일차 기록](devlog/day02-2026-10-25.md)

현재는 평가 정의만 있고 실제 검색·에이전트 평가 결과는 없다. 개선 전후 차이를 임의로 채우지 않는다. 첫 평가에서 의미 있는 문제가 발견되면 질문/고정 데이터 버전, 잘못된 검색 또는 동작, 확인한 원인, 바꾼 내용, 같은 조건의 재검증 결과·남은 한계를 해당 항목에 기록하고 일차 로그에서 연결한다.

### D06. Chroma 실행 폴더 대신 고정 벡터로 복원 (2026-10-25)

- 선택: 실제 Chroma의 저장 벡터를 약 350KB JSONL로 내보내고, 모델·차원·청크/벡터 해시를 명세로 연결한다. Chroma 바이너리를 통째로 커밋하거나 배포마다 재임베딩하는 대안은 로컬 실행 상태와 의존성·비용을 불필요하게 묶어 채택하지 않았다.
- 복원은 파일 전체를 검증하고 미적재 항목만 명시적 벡터로 추가한다. 기존 항목의 벡터가 다르면 덮어쓰지 않고 중단한다. 문서 임베딩 함수를 호출하지 않으므로 키·캐시가 없어도 정책 인덱스 복원이 가능하다. 새 자연어 질문의 임베딩은 여전히 별도 API가 필요하다.
- JSONL은 Git 체크아웃 후에도 바이트 해시가 유지되도록 LF를 지정한다. 입력 도구는 기존 계약과 일치하도록 query 최대 1,000자로 통일했다. 실제 인덱스 준비 실패/캐시 미스와 시스템 예외를 not_ready/error로 구분하며 근거 없음으로 숨기지 않는다.
- 실제 확인: 빈 Chroma 복원 11개, 반복 복원 0개. 기존 질문 캐시만 사용한 14문항의 검색 결과·순서가 동일하고 API 호출은 0회였다. 별도 자동 테스트에서는 캐시 없이 고정 실제 벡터를 복원하고 벡터 직접 조회했다. 파일 해시·모델·차원·입력 해시·ID 손상은 적재 전에 거부했다. [검증 보고서](rag-restore-validation.json)
- 테스트 작성 중 파일을 동일하게 다시 직렬화해 손상이 생기지 않아 1개 검사가 실패했다. 손상 사례가 실제 바이트를 바꾸도록 고친 뒤 관련 검사는 통과했다. 애플리케이션의 해시 검증 실패는 아니었다. 실제 컨테이너 시작 복원은 배포 일차 범위다.

### D07. 기본 상담을 직접 만든 StateGraph 하나로 제어 (2026-10-30)

- 선택: 모델이 엄격한 NextAction 스키마로 행동을 제안하고 LangGraph의 판단 노드가 서버 제약을 확인해 두 LangChain 도구를 invoke한다. native tool_calls를 곧바로 실행하거나 create_agent/AgentExecutor를 그래프 안에 중첩하는 대신 상태·분기·반복을 직접 설명할 수 있도록 한 실행 루프만 둔다.
- 서버는 주문 객체·출처 메타데이터·실행 내역을 직접 채우고, 조회 1회/검색 2회/전체 3회·모델 4회 제한을 실행 전에 검사한다. 인용 검증 실패나 준비/시스템 오류는 고객 초안을 숨기며 error를 근거 없음으로 취급하지 않는다. 규칙 ID 연결만으로 자유 문장의 의미까지 정확하다고 판단하지 않는다.
- 기본 상담도 API를 명시적으로 허용해야 실행한다. 자동 테스트는 고정 판단/도구를 주입하며, 실제 소규모 smoke는 프로세스에서만 허용한다. 별도 대화 이력·체크포인트·멀티 에이전트·새 패키지는 추가하지 않았다.
- 최종 자동 테스트 60개·프런트 타입/계약/빌드 통과. 실제 4사례는 상태·도구 횟수 일치와 문장 수동 검토를 확인했다. 최초 결과에서 재현할 실제 실패가 없어 개선 전후 점수는 만들지 않았다. 전체 24사례와 브라우저 검수는 다음 범위다. [일차 기록](devlog/day03-2026-10-30.md), [상태와 흐름](agent-flow.md)

### 2026-10-30 · 사용자 관찰: 조사 하나에 따른 결과 변화 (수정 보류)

### D08. 조회 후 근거 누락과 근거 부족 응답 오류를 분리해 수정 (2026-10-30)

- 앞선 수정 보류 표기는 평가 당시 상태다. 이후 사용자가 후속 작업을 요청해 O04/E01을 관측 정보만 보강한 실제 진단으로 다시 실행했다. 기존 질문/정답·최초 보고서는 보존했다.
- 확인: O04는 조회한 날짜를 답변했으나 정책 검색이 없어 근거 계약에서 차단됐다. E01은 계획 스키마가 허용한 recommendation=null을 최종 응답이 허용하지 않아 검증 실패했다. 타입 이름/필드만 저장한 진단으로 정확한 오류 위치를 확인했다.
- 선택: O04는 남은 모델 한도 안에서 feedback으로 재판단하고, E01은 근거 부족 추천의 null만 고정 절차 안내로 보완한다. 임의 인용 추가·무제한 모델 재시도·근거 없는 금액 생성을 하지 않는다. 입력 주문번호는 이번 문의 대상이라는 기준을 서버와 UI에 명시해 조회 생략도 막았다.
- 검증: 68개 회귀와 프런트 타입/계약/빌드 통과. 실제 전체 구조 결과는 v1 18/24 → v2 23/24 → v3 22/24다. 중간 실행보다 최종 숫자가 낮아진 것도 보존한다. O09 기간 경과 구분은 개선됐고 P03/O08은 여전히 실패다. R02의 상태 의미 혼선도 별도 내용 검토에서 남겼다.
- 조회/검색을 모두 고정해 처리하는 대안 대신 서버 제약 + 모델 선택을 유지했다. nullable 계획 필드 전체를 둘로 나누는 대안보다 확인된 부정 응답 경로만 제한적으로 복구했다. 진단은 고객 응답을 바꾸거나 원시 오류를 노출하지 않는다. [원인·재현·전후·제한](agent-fixes-2026-10-30.md)

### D09. O08의 확인 질문과 부정 상태를 일치시킴 (2026-10-30)

### D10. 검색된 관련 조건을 답변까지 보존 (2026-10-30)

- 증상/원인: P03은 두 기한의 근거와 표준 조건을 모두 검색했지만, 모델이 반품 절차만 적용 인용해 조건·예외 설명을 누락했다. 청크 연결은 검색 확장에만 사용되고 모델 입력·최종 적용 검사에는 전달되지 않았다.
- 선택: 기존 related_rule_groups를 내부 입력으로 노출하고, 실제 적용한 정책의 관련 근거 인용을 서버에서 확인한다. 현재 반품 절차 → 표준 조건·예외 연결에 적용한다. 이미 검색된 근거면 모델이 설명을 보완하고, 없는 근거면 모델이 재검색을 선택한다. 판단 4회·검색 2회·전체 도구 3회를 늘리지 않으며 계속 누락하면 초안 없이 근거 부족으로 종료한다.
- 대안: 프롬프트만 강조하면 같은 누락을 서버가 계속 허용한다. 모든 검색 후보를 무조건 인용하면 관련 없는 정책이 답변에 섞인다. 서버에서 ID만 자동 추가하면 설명 누락을 숨긴다. 따라서 실제 적용 인용에 연결된 조건만 검증하고 문장 생성은 모델에 맡겼다. 인용 검사가 모든 문장의 의미를 보장하지는 않는다.
- 검증: 수정 전 기존 제안 재생 등 3개 실패 → 수정 후 새 5개 포함 전체 77개 통과. Ruff·TS/계약 검사 통과. 실제 P03/O08 2/2 구조 통과와 수동 내용 검토·Zod 검증을 확인했다. 실제 P03은 첫 finish부터 조건과 두 인용을 작성했고 feedback 자체는 고정 재생으로 확인했다. 전체 평가/조사 민감도/R02는 이번 범위가 아니다. [상세 전후·제한](agent-fixes-2026-10-30.md#p03-follow-up)

### D11. 상태 코드 의미를 모델 추정에 맡기지 않고 조회 사실로 전달 (2026-10-30)

- 확인: P03 수정 후 전체 평가 v4는 23/24였고 O08이 실패했다. R02는 구조 통과지만 processing의 한국어 의미를 미확인으로 설명했다. 기존 모델 입력에는 내부 코드만 있고 한국어 매핑은 화면에만 있었다. 출력에서 확인한 혼선과 입력 누락은 사실이며 이것만이 모델 오류의 유일한 원인이라고 단정하지 않는다.
- 선택: 프로젝트가 정의한 7개 코드의 한국어 표시와 품목별 기록 시각을 모델 입력 order_status_facts에 명시한다. 실제 조회 객체/DB/API 계약은 그대로 두고 unknown만 상태 확인 필요로 전달한다. 이미 확인된 코드의 번역 때문에 정책을 재검색하지 않으며, 상태와 카드/다품목 예외를 구분한다. 현재 상태가 달라질 수 있다는 말로 기록 자체의 의미를 미확인 처리하지 않게 한다.
- 대안: 상태 의미를 LLM이 매번 번역하게 두면 알려진 사실을 불확실성으로 바꿀 수 있다. 상태 정책을 무조건 추가 검색하면 R02의 불필요한 재검색 금지와 충돌한다. 자유 문장을 문자열 치환하면 문맥/부정문을 깨뜨릴 수 있다. 따라서 입력 사실을 명확히 하고 실제 출력은 따로 읽어 검증한다. 자연어 의미를 전부 서버가 검증하는 기능은 추가하지 않는다.
- 추가 발견: v4 O08은 확인 권고 문장만 쓰고 구조화된 질문은 비웠다. 상태 보정의 입력 조건 자체가 없으므로 v5 지침에 needs_information+other 질문을 명시했다. 문장에서 질문을 추출해 서버가 채우는 방식은 적용하지 않았다.

### D12. 질문에 필요한 정책만 적용하고 요약의 결합 조건을 보존 (2026-10-30)

- 확인: v5 P04는 파손 문의 경로만 물었는데 일반 반품 조건까지 적용했다. 보안 기능 활성화와 비활성화 불가의 결합 조건도 활성화만으로 줄였다. 같은 실제 평가 P01은 무료라는 사실은 맞지만 유료 질문에 네로 시작했다. 자동 구조 검사는 두 사례 모두 통과했으므로 의미 검토 문제로 구분했다.
- 선택: 프롬프트 v6에서 실제 적용할 정책을 질문 범위로 한정하고, 적용하는 정책의 결합 조건·한정·예외는 보존하도록 한다. 파손 상담 경로에 일반 반품 요건을 덧붙이지 않되, 반품 기한/조건을 묻는 P03의 관련 정책 적용 검사는 유지한다. 고객 초안은 예/아니요 대신 핵심 사실로 시작하게 한다. 프롬프트 전체 재구성은 보류한다.
- 대안: 검색 후보에서 일반 반품 문서를 제거하면 P03 등 필요한 조건도 잃을 수 있다. 서버가 문장을 삭제하거나 예/아니요를 치환하면 문맥과 근거를 깨뜨릴 수 있다. 검색 결과·답변 계약은 그대로 두고 모델의 적용 범위와 표현을 보강한 뒤 실제 출력을 읽어 확인한다. 문장 의미를 서버가 완전히 보장하는 규칙은 추가하지 않았다.
- 실제 검증: 6사례 구조 통과와 수동 검토, pytest 80개·Ruff·실제 Zod 6개 통과. P04는 상담 경로만 적용했고 P01은 사실로 시작했다. P03/O07의 보안 결합 조건과 O08/R02 보강을 유지했다. v6 전체 평가는 재실행하지 않아 v5 24/24와 구분한다. [전후·원본·제한](p04-p01-fixes-2026-10-30.md)

### D13. 배포 시작 전에 고정 DB·벡터를 로컬 복원/검증 (2026-10-30)

- 문제: 기존 Dockerfile은 주문 SQL만 복사·초기화해 실제 정책 도구에 필요한 artifacts/Chroma가 빠져 있었다. 수집일/출처와 실제 벡터가 저장소에 있어도 실행 이미지에는 포함되지 않았다.
- 선택: Node 빌드와 Python 잠금 설치는 유지하고 고정 청크/벡터/명세를 복사한다. prepare_runtime이 기존 주문 초기화와 restore_vectors를 재사용한다. 빌드에는 --prepare-only를 사용하고 시작 시 같은 검증/복원을 거친 뒤 os.execv로 Uvicorn 단일 프로세스로 전환한다. 데이터가 비면 재구성하고, 현재 고정 자료나 기존 대상 데이터가 불일치하면 시작을 중단한다. 복원 중 API 허용은 항상 false다.

### D20. 출처 인용은 위치 이동과 본문 펼침/초점을 함께 처리 (2026-11-02)

- 증상/원인: 인용의 `href="#근거ID"`는 접힌 `details` 자체를 가리켰다. 위치만 이동하고 `open`은 없어 본문을 바로 읽을 수 없었다. Chromium에서 Enter로 활성화한 뒤 펼침 속성 검사가 실패해 재현했다. 근거 ID/본문/API 계약의 오류는 아니다.
- 선택: 컴포넌트 ref의 `Map<string, HTMLDetailsElement>`에 출처 요소를 연결한다. 인용 클릭 시 해당 요소만 펼치고 `tabIndex=-1`로 프로그램 초점을 줄 수 있게 했다. `href`는 유지해 URL 해시/기본 이동을 보존하며, 키보드 Enter도 같은 클릭 처리를 사용한다. ref 해제 때 Map에서 삭제한다.
- 대안: 모든 출처를 항상 펼치면 미적용 검색 후보까지 긴 본문을 읽게 된다. 수동 펼침만 유지하면 인용에서 본문으로 가는 동작이 끝나지 않는다. 전역 DOM 검색보다 현재 컴포넌트의 typed ref로 대상을 한정했다. 정책 선택·응답 계약은 바꾸지 않는다.
- 검증 전후: 최초 화면 검사 15개 중 인용 펼침 1개 실패→수정 후 통과. 과거 P03의 적용 근거 2개 클릭과 O06 품목별 상태/날짜를 더해 최종 17/17 통과. TypeScript·계약·빌드 통과. 타입 검사는 DOM 종류/누락 접근을, 실제 브라우저 검사는 펼침/초점/본문 연결을 확인한다.
